Most course examples retrieve from a tidy demo corpus and stop when the answer looks plausible. This one retrieves from a live research corpus with real defects in it — and its most useful output is not an answer, but a list of the places where the corpus contradicts itself.

Why a second worked example

Your capstone runs on a document collection you chose in Week 1. This one runs on a corpus with an unusual property: every claim already carries its own epistemic status. The Principia Orthogona papers tag each assertion [DATA], [MODEL], [OPEN], [VALUE PREMISE], or [ASSUMPTION], cite DOIs, and mark which theorems a Lean kernel has actually checked.

That changes what retrieval can do. A normal RAG system returns text and hopes the model uses it responsibly. This one returns text with its status attached — and can refuse to let an [OPEN] claim be presented as established. Read it as one answer to the Week 1 question — when should the system decline? — implemented rather than discussed.

Module map

ModuleDoesCourse week
ingest.py Parses HTML/MD/TeX/Lean into claims rather than fixed-size chunks. Each record keeps tags, DOI, working-paper number, extracted constants, and a trust tier 0–4. Week 3 — the chunking decision, made on semantics instead of token count
retrieve.py Okapi BM25 in pure Python, then a mild trust re-weighting, then a context block carrying a refusal contract the generator must satisfy. Weeks 2 & 4 — the baseline, and what "fusion" looks like when the second signal is provenance rather than vectors
audit.py Seven checks (C1–C7) over the ingested claims: constant drift, DOI incoherence, dangling references, tag laundering, verification drift, orphan constants, stale hedges. Week 5 — evaluation, pointed at the corpus instead of the retriever
flow.py Dependency graph over claims, constants, DOIs and Lean files. Ask what breaks if a constant changes; get the closure and a work order. Week 6 — multihop, as dependency traversal rather than query decomposition
handoff.py Session-state protocol so parallel operators inherit decisions instead of re-deriving them. Week 8 — the operational reality nobody's demo includes

Three design decisions worth arguing with

1 · A chunk is a claim, not a window

Fixed-size chunking splits a sentence from the tag that qualifies it. If the sentence "the boundary is 0.776" lands in one chunk and "[OPEN] — this value is not established" lands in the next, retrieval has manufactured a false certainty. So chunking follows document structure, and each chunk inherits its weakest tag: one [OPEN] contaminates the claim.

2 · BM25, deliberately, with no embeddings

Not because dense retrieval is worse — Week 3 shows where it wins — but because for a corpus that must be citable, exact and reproducible beats marginally better recall. The same query returns the same passages next year. A dense reranker can be layered on later without touching the contract; that is left as an exercise, and it is a real one.

3 · The context block carries a contract

RETRIEVAL CONTRACT — binding on the answer you generate:
1. Cite by [source · tag · DOI] for every factual sentence.
2. A claim tagged OPEN is NOT established. Never launder OPEN into DATA.
3. Do not state a numeric constant absent from the context below.
4. If two blocks disagree on a constant, report the conflict and its
   sources; do not silently pick one.
5. VERIFIED means machine-checked by the Lean kernel. Nothing else.

Rule 4 is the one that matters. Ordinary RAG, handed two contradictory retrieved passages, picks one — usually the higher-ranked — and states it confidently. That is the failure mode this corpus is most exposed to, so it is the one the contract addresses directly.

The reverse direction: the corpus audits itself

Retrieval is half the system. The other half runs backwards: the same claim-level index is the input to a defect sweep. Run on a 240-claim slice, with two defects planted to confirm detection, it reported:

[HIGH] C1  constant r* asserted with 4 distinct values:
           0.773 vs 0.7732 vs 0.77594 vs 0.8
       where: GTCT_2026_v4.tex, SITE_ERRATA.md,
              certify_rstar.py, stale_findings.md

[HIGH] C5  prose claims ForcedUrgency.lean is sorry-free;
           the ingested ForcedUrgency.lean contains a sorry

[MED ] C2  WP-32 cited under 2 different DOIs

The r* finding was not planted. One physical constant appeared at four different values across four files, and it had taken a full working session to chase down by hand. The sweep finds it in under a second.

The false positive that teaches the most

A corrected document quotes the value it retires — "supersedes the 0.7732 reported in V1–V3." A naive drift detector flags that correction as a contradiction, which is exactly backwards: the file doing the right thing gets the alarm. The fix is a suppression rule for correction notices. Every evaluation harness you build will have a class like this. Find it before you trust the numbers, and write it down where the next person will see it.

What flows: invalidation, not documents

An index is static, and nobody reads a corpus — not a person, not a retriever. What has to travel is the invalidation signal. flow.py is make for a body of knowledge: claims depend on constants, DOIs, and Lean files; change a root and the dependent closure is stale by construction.

$ python3 flow.py chunks.jsonl --change "const:r*"
changing const:r* invalidates 10 claims across 4 files:
  GTCT_2026_v4.tex
  SITE_ERRATA.md
  certify_rstar.py
  stale_findings.md

$ python3 flow.py chunks.jsonl --change "const:r*" --order
# → a markdown work order with completion criteria

The single correction that motivated this took nine edits across papers, figures, captions, a Lean constant, and three copies of one web page. They were found one at a time, over several sessions, each discovery arriving as an unpleasant surprise. The closure computes all of them at once — which is the difference between a retrieval demo and a system someone depends on.

The transferable lesson

Ask of your own capstone corpus: what is the root node here? A price, a threshold, a schema version, a model name, a regulation. Then ask whether your system can answer "what breaks if this changes?" If it cannot, it is a search box. Retrieval that knows its own dependency structure is worth more than retrieval that scores marginally better on recall@10.

Run it yourself

# any corpus of .html / .md / .tex / .lean
python3 ingest.py   ./my-corpus        -o chunks.jsonl
python3 audit.py    chunks.jsonl --severity HIGH
python3 retrieve.py chunks.jsonl "your question" --context
python3 flow.py     chunks.jsonl --roots

Pure standard library. No API key, no embedding model, no network call. It will run on a laptop with no internet, which is a property worth preserving longer than it is fashionable to.

Honest limits

  • OPEN BM25 is lexical. Synonym-heavy queries miss. Adding a dense reranker is the obvious next increment and does not require changing the contract.
  • OPEN Constant extraction is regex-based over seven tracked constants. Broadening it is mechanical but unglamorous.
  • DATA The trust tier is inherited from the author's own tags. It measures labeling discipline, not truth. A mislabeled claim retrieves as mislabeled — the system cannot rescue a corpus that lies to it.
  • OPEN The audit finds contradiction, never falsehood. A corpus can be perfectly self-consistent and entirely wrong.

That last one is the boundary worth internalising before Week 5. Evaluation tells you whether a system is behaving consistently with its own data. It cannot tell you the data is right. Knowing which question you have answered is most of the engineering judgment this course is trying to build.
